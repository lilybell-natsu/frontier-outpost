# 2026-09-11 v0.22.0 レベルアップ不具合の真因修正と置き場南端移動

## 経緯
v0.21.0に対するフィードバック:

- レベルアップが行えないので修正
- 木材置きエリアや、売買エリアは、売買カウンターの南端側に移動
- 再配置に伴ってコンベアの描き方も変える
- 木材ボックスから木材置きエリアまでのコンベアは直線的に伸ばす(折れ線的な配置にする)

## 実装内容

### 「レベルアップできない」不具合の真因調査・修正
v0.21.0で「所持Gが足りているのにレベルアップできない」不具合の対策(`renderResBar()`から効率化
タブ・雇用タブを併せて再描画する)を行ったが、同じ症状が再度報告された。Browserペインで実際の
UIクリックを使って再現を試みたところ、**コード自体には問題がなく、v0.21.0の対策は正しく機能して
いる**ことを確認した(ゴールドを直接加算→再クリックのシーケンスで、効率化タブの複数のボタンが
正しく連続してレベルアップできることを確認)。

そのうえで、テスト中に**別の真因を発見**した: `sw.js`のfetchハンドラは「network-first」のつもりで
`fetch(event.request)`を呼んでいたが、**cacheオプションを指定していなかったため、ブラウザ自身の
HTTPキャッシュ(Service Workerのキャッシュとは別レイヤー)がこのfetch呼び出し自体に古い応答を
返してしまうことがあった**。実際に「同じタブを使い回して`navigate()`を繰り返すと、Service Worker
を明示的に登録解除・キャッシュ削除しても、なお編集前の古いJSが実行され続ける」という形で再現に
成功した(新しいタブで開き直すと正しく最新版が読み込まれることから、真因はブラウザのHTTP
キャッシュ層であると特定)。GitHub Pagesは`Cache-Control`ヘッダーを明示的に付けないため、
ヒューリスティックキャッシュにより実際のユーザー環境でも同様の「コードを直しても反映されない」
症状が起こりうると判断した。

**修正**: `sw.js`のfetchハンドラを`fetch(event.request, { cache: "no-store" })`に変更し、HTTP
キャッシュを完全に迂回して常に本当に最新のバイト列を取得するようにした。あわせて`CACHE_NAME`を
`v2→v3`に更新し、既存ユーザーの古いCacheStorageエントリも破棄させる。

## 木材置き場・売買ポイントを南端側へ移動
- `DEPOSIT_PT`(木材を置くポイント)・`TRADE_PT`(レーン0=プレイヤー用の売買ポイント)を、
  カウンター北端(`COUNTER_Z_FROM`、拠点拡張で動く側)から南端(`COUNTER_Z_TO`、扉・木材収集
  ボックスに近い側、拠点拡張の対象外で常に固定)へ移動
- `tradeLaneZ(i)`の基準点を`COUNTER_Z_FROM+1+i*GAP`から`COUNTER_Z_TO-1-i*GAP`に変更(レーン0
  =置き場のすぐ北、レーン1以降はさらに北へ順に並ぶ。並び方自体は従来どおりで、向きだけ反転)
- `COUNTER_Z_TO`は拠点拡張の影響を受けない固定`const`のため、**`DEPOSIT_PT`/`TRADE_PT`も
  `let`(拠点拡張のたびに`recomputeBaseLayout()`で再計算)から`const`(起動時に一度だけ計算)へ
  変更できた**。`recomputeBaseLayout()`からは両者の再計算コードを削除し、関数の責務を
  `BASE_MIN_Z`/`COUNTER_Z_FROM`/`PLAZA_MIN_Z`(実際に拠点拡張で動くもの)だけに絞った
- `AUTO_BOX_GOLD_PT`(G収集ボックス)は元々南端寄りに置かれていたため座標は変更していないが、
  自動化NPCの列が新レイアウトでも衝突しないことを確認したうえでコメントを更新
- `repositionAllTradeLanes()`は実質的に何もしなくなった(レーン座標が拠点拡張で動かなくなった
  ため)が、将来レイアウトが変わった場合の安全策として、拠点拡張購入直後に呼び続ける形は残した

## ベルトコンベアを折れ線(L字)の直線区間に描き直し
- 置き場が南端(木材収集ボックスに近い側)へ移動したことで、両者の距離が大幅に縮まった。これに
  合わせて、従来の「斜め1本」の導線を、**軸に沿った2区間の折れ線**に変更:
  1. 木材収集ボックス(`AUTO_BOX_WOOD_PT`)から、置き場と同じx座標まで、ボックスと同じ行(z)を
     直進する区間
  2. そこ(折れ点)から、置き場(`DEPOSIT_PT`)のzまで直進する区間(今回のレイアウトでは1マスのみ)
- `addBeltSegment(group, fromPt, toPt)`が、軸平行な1区間の見た目(ベルト本体+スラット)を
  `BoxGeometry`の寸法だけで組み立てる(回転を使わない設計に変更。旧実装は`Math.atan2`で
  グループ全体を回転させる斜めの1本だったが、軸平行な区間だけを扱うなら回転は不要で、実装も
  単純になった)
- 運搬中の木材(3個)は、経路全体の長さ(区間1+区間2)を1周期として、現在の位置がどちらの区間に
  あるかで単純な線形補間先を切り替える`updateTransportBeltVisual()`に書き直した。区間をまたぐ
  瞬間も座標が連続するため、見た目上の跳躍は起きない
- 拠点拡張後もベルトを作り直す`rebuildTransportBelt()`の呼び出しは、現状は実質的に何もしない
  (`DEPOSIT_PT`/`AUTO_BOX_WOOD_PT`がどちらも固定座標になったため)が、将来レイアウトが変わった
  場合の安全策としてそのまま残した

## 動作確認
Browserペイン(localhost:8795)で確認。一時的なデバッグフック(`window.__giveGold`/`__dbg`/
`__points`/`__buyTransport`/`__buyBaseExpansion`/`__beltInfo`/`__setBoxWood`/`__testInteract`)
を仕込んで検証後にすべて削除(削除後にGrepで`window\.__`の残存なしを確認)。

- **キャッシュ不具合の再現・修正確認**: 同一タブでの`navigate()`繰り返しにより「Service Worker
  登録解除・キャッシュ削除後もなお古いJSが実行される」ことを実際に再現。修正後、新しいタブで
  開いた場合・既存タブ経由でService Workerが更新された場合の両方で、最新のコード(デバッグフック
  を含む)が正しく読み込まれることを確認
- **レベルアップ不具合の再確認**: ゴールドを持たせたうえで、実際のUIクリック(`computer`
  left_click、debug hookではない)で「木材の確保量」を2回連続レベルアップ、拠点拡張・木材自動
  運搬も実際のクリックでレベルアップできることを確認(いずれもDOM再描画後の新しいボタン参照に
  対して正しくクリックが機能した)
- **座標の確認**: `DEPOSIT_PT{x:-3,z:2}`/`TRADE_PT{x:-3,z:1}`/`AUTO_BOX_WOOD_PT{x:2,z:3}`/
  折れ点`{x:-3,z:3}`が理論値どおりであることを確認。拠点拡張を購入しても`DEPOSIT_PT`/`TRADE_PT`/
  折れ点が変化しない(固定)ことを確認
- **ベルト形状の確認**: `lenA=5`(木材ボックス→折れ点)・`total=6`(折れ点→置き場の1マス分を
  加算)が理論値と一致することを確認。運搬中の木材が区間1(z一定・x変化)→区間2(x一定・z変化)
  へ連続的に移動することを、フレームごとの座標変化として確認
- **接続点での実際の操作確認**: プレイヤーを新しい`DEPOSIT_PT`/`TRADE_PT`へ実際に配置して
  `updateInteractions()`を呼び、木材の置き場デポジット(carryWood→resources.wood)・売買ポイント
  でのお客さん対応("お客さんへ渡し中…"表示)がどちらも正しく機能することを確認
- コンソールエラーなし(全工程で確認)
